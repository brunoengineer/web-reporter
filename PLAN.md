# Web Reporter — Implementation Plan

A Chrome extension that lets a QA engineer record a manual-test session locally and export a **single self-contained `.html` file** to hand to a developer. No server, no cloud, no link — everything stays in the browser until the user clicks Export.

---

## 1. Goals & non-goals

### Goals
- One-click **Start / Stop** recording from the toolbar.
- Capture during a session:
  - Page & browser metadata (URL, title, user agent, viewport, OS, locale, timezone).
  - Console output (log / warn / error / unhandled rejections).
  - User actions — clicks, key events, navigation, form submits. **Input values redacted by default.**
  - Screenshots: manual on demand + automatic on console errors.
  - Optional HAR-lite network log (see §4).
  - Free-text notes from the QA (title, severity, repro steps, expected vs actual).
- Export as a **single `.html` file** with everything embedded. Opens offline in any browser by double-clicking.
- Report viewer designed for the developer who has 30 seconds to triage.
- 100% local. No `fetch` to any third-party endpoint, ever.

### Non-goals
- **Video recording.** Auto-screenshot on errors + manual screenshots cover bug-repro needs without the complexity (offscreen document, MediaRecorder, IndexedDB chunked storage, 20 MB blobs).
- Editing/trimming media inside the extension.
- Cross-tab session recording. MV3 makes this hard; defer.
- Cloud upload or share link — explicitly excluded.
- Mobile / non-Chromium browsers.

---

## 2. Language & stack

### Language: **TypeScript**
The extension code runs in 3 separate contexts (service worker, content script, popup) that talk via `chrome.runtime.sendMessage`. Typing the message contracts catches the most common MV3 bug class at compile time. No runtime cost.

### UI: **Vanilla TS + plain HTML/CSS** for the popup AND the report viewer
The popup is start/stop, take-screenshot, a notes textarea, and an export button. The report viewer is tabs reading a JSON object and rendering tables / a timeline. A framework would be more code than the UI itself.

### Build tooling: **Vite + `@crxjs/vite-plugin`**
- HMR for the popup, automatic `manifest.json` handling, MV3-aware.
- Standard, well-supported, fastest path to a working dev loop.

### Other libraries
- **`vitest`** — unit tests for the redaction helpers and report builder.
- That's it. No JSZip (single HTML), no rrweb (simple action log), no UI framework, no chart library (hand-rolled inline SVG).

## 3. Architecture

Manifest V3 forces this shape:

| Component | Purpose |
|---|---|
| **`manifest.json`** | MV3 config + permissions. Generated by crxjs from `manifest.config.ts`. |
| **Popup** (`src/popup/`) | UI: Start/Stop, take screenshot, edit title & notes, severity tag, Export. Plain HTML + TS. |
| **Service worker** (`src/background/`) | Session state machine, coordinates capture, builds the final HTML on export. |
| **Content script** (`src/content/`) | Injected into the active tab. Hooks console + actions + (phase 2) network. Sends events to the SW. |
| **Report viewer** (`src/report/`) | Static `template.html` + `viewer.ts` + `viewer.css`. The exporter inlines all three plus the captured data into one self-contained file. |

### Data flow
```
[content script] -- events --> [service worker] -- aggregates --> [chrome.storage / IndexedDB]
                                       ^
                                       |
[popup] -- start/stop/screenshot/export commands --+
                                       |
                                       v
                       on Export: SW reads all data, fills the report template,
                                  triggers download via chrome.downloads
```

### Storage
- **`chrome.storage.local`** — small things: session metadata, settings, event log.
- **IndexedDB** — screenshots (PNG blobs).

## 4. Capture details — APIs and tradeoffs

### Screenshots
- `chrome.tabs.captureVisibleTab` — viewport only, no extra permissions beyond `activeTab`.
- Auto-trigger on `console.error` and unhandled rejection.
- Full-page (scroll + stitch) is a phase-3 nice-to-have.

### Console output
- Inject a small page-context script (`world: "MAIN"`) that wraps `console.log/warn/error` and listens for `error` / `unhandledrejection`. Forward via `postMessage` → content script → service worker.
- Wrapping must run in **page context**, not the isolated content-script world, or it sees nothing.

### User actions
- `click` (with selector + visible text), `input` (selector + length only — **value redacted**), `submit`, navigation (`popstate`, `pushState` patch).
- That's it. No DOM snapshotting.

### Network — HAR-lite (phase 2)
Three options for HAR; only one is non-intrusive:
1. `chrome.debugger` API → full HAR, but Chrome shows a permanent yellow "being debugged" banner. Bad UX for QA work.
2. DevTools panel → clean HAR, but the user must keep DevTools open the whole session.
3. **Patch `fetch` / `XMLHttpRequest`** in page context → no banner. Misses pre-injection requests, `<img>` / `<script>` resource loads, and preflights. Labeled "HAR-lite" in the report so devs aren't misled.

**Plan: ship phase 2 with option 3.** Option 1 can be an opt-in toggle later.

### Privacy / redaction (default-on)
- `<input type="password">` values: never recorded, no opt-out.
- Other inputs: log `{selector, length}`, not the value.
- Redact `Authorization`, `Cookie`, `Set-Cookie` headers.
- "Reveal raw values" toggle is **off** by default and only affects what gets embedded in the export.

## 5. Report — design & contents

This is the artifact the developer actually sees. Concise, scannable, organized.

### File output
`web-reporter-<slug>-<YYYYMMDD-HHmm>.html` — one file. Internally:

```html
<!DOCTYPE html>
<html>
<head>
  <style>/* inlined viewer.css */</style>
</head>
<body>
  <div id="app"></div>
  <script id="session" type="application/json">{ ...session metadata, events, console, network... }</script>
  <script id="screenshots" type="application/json">[ "data:image/png;base64,...", ... ]</script>
  <script>/* inlined viewer.js — reads the above and renders the UI */</script>
</body>
</html>
```

### Layout
Left sidebar nav, main scrolling area, **summary card pinned at top**.

```
┌──────────────────────────────────────────────────────────────┐
│ ▶ Login fails after submit                       [HIGH]      │
│   example.com/checkout · 2026-05-09 14:02 · 3m 22s           │
│   Chrome 128 · Windows 11 · 1440×900 · en-US · UTC-3         │
│   ⚠ 3 errors   📋 18 actions   📷 4 shots   🔁 2 navs        │
└──────────────────────────────────────────────────────────────┘
[Summary] [Repro Steps] [Timeline] [Console] [Actions] [Screenshots] [Notes] [Raw JSON]
```

### Sections (in priority order for a developer)

1. **Summary card** (always visible). Title, severity, URL, env, duration, headline counts, mini-sparkline of errors over time. The 5-second triage view.
2. **Repro Steps** — auto-generated numbered list from the action log, with console errors and screenshots inlined at the moment they happened. Editable from the popup before export. *This is the most important section.*
   ```
   1. Navigate to /login
   2. Click [Sign In]
   3. Type into #email (24 chars)
   4. Type into #password (••• redacted)
   5. Click [Submit]
      ⚠ Cannot read property 'token' of undefined   (auth.js:142)
      📷 screenshot-3
   6. Click [Try again] — same error
   ```
3. **Timeline** — single horizontal SVG strip with colored markers (action / error / screenshot / nav). Click a marker → jumps to that entry. The visual spine that ties everything together.
4. **Console** — filter pills (All / Errors / Warnings / Logs), table with timestamp · level · message · source. Stack traces collapsed by default.
5. **Actions** — full table view of every recorded event. Small donut chart: clicks vs inputs vs navs.
6. **Screenshots** — thumbnail grid; click to enlarge. Each tagged auto/manual with timestamp.
7. **Notes** — QA's free-text repro notes, expected vs actual.
8. **Raw JSON** — collapsed by default. For the dev who wants to grep.

### Charts (kept minimal and purposeful)
- Errors-over-time mini-sparkline in the summary card.
- Actions-by-type donut in the Actions section.
- Both hand-rolled inline SVG, ~30 lines each. No library.

### Visual style
- Light theme + dark toggle.
- Fonts: `system-ui` for body, `JetBrains Mono` / `Consolas` / `monospace` fallback for code, selectors, URLs.
- One accent color (teal). Semantic: red for errors, amber for warnings, green for success/200s, gray for neutral.
- Cards with soft borders, generous padding. No drop shadows.
- Severity badges: HIGH (red) / MEDIUM (amber) / LOW (gray).
- No external fonts. System stack only (works offline forever).

### Tech (still no framework)
- Functions that build DOM nodes via `document.createElement` — no string concatenation, no XSS risk if a console message contains `<script>`.
- All CSS in one inlined `<style>` tag, all JS in one inlined `<script>` — fully self-contained.
- Deep-link via `#section-id` so users can share a specific tab in chat (still works offline; just a hash).

### Size considerations
- Screenshots at PNG quality ~80%: 50–200 KB each base64. 20 screenshots ≈ 2–4 MB.
- Typical export: **<5 MB**. No need for size warnings in the common case.
- Hard ceiling we'll warn at: **20 MB** (e.g. screenshot-heavy session). Above that, suggest culling shots.

### Why single HTML
- One file is dramatically easier to share (drag into Slack, attach to Jira) — no "extract first" step.
- Devs open by double-clicking.
- We give up nothing important.

## 6. Phased delivery

### Phase 1 — MVP
- Vite + crxjs + TS scaffold.
- Manifest V3 with `activeTab`, `storage`, `scripting`, `tabs`, `downloads`.
- Popup: Start / Stop / Take Screenshot / Export, plus title + severity + notes.
- Capture: page metadata, console output, user-action log (redacted), manual screenshots, **auto-screenshot on console error**.
- Report viewer: Summary, Repro Steps, Timeline, Console, Actions, Screenshots, Notes, Raw JSON.
- Export: single self-contained HTML.
- **Done when:** a QA can record a session on any site, hit Export, double-click the file, and see a coherent report.

### Phase 2 — HAR-lite
- Patch `fetch` / `XMLHttpRequest` from a page-context script.
- Network tab in the report (table: method · status · url · time · size). Filter pills.
- Timeline gains network markers.

### Phase 3 — Polish
- Settings page: redaction rules, screenshot quality, dark/light default.
- "Copy as markdown" button in the report viewer for Jira / GitHub bug templates.
- Full-page screenshots (scroll + stitch).
- Opt-in `chrome.debugger` full-HAR toggle with a clear warning about the banner.

### Loading in Chrome
1. `npm install`
2. `npm run dev` → builds to `dist/` and watches.
3. `chrome://extensions` → enable Developer mode → **Load unpacked** → pick `dist/`.
4. Edit code → popup hot-reloads; for SW / content-script changes, click reload on the extension card.
5. `npm run build` → production `dist/`.

## 8. Risks / open questions

- **Service-worker lifecycle.** MV3 SWs can be killed mid-session. Mitigation: persist state to `chrome.storage` after every event; resume on wake. Verify under Chrome's idle-kill timeout.
- **Cross-origin iframes.** Page-context hooks need `world: "MAIN"`; some sites' CSPs will block it. Document the limitation rather than pretend it works.
- **SPA navigation.** History-API navigation doesn't reload the content script — make sure listeners survive `pushState`.
- **Report bundling.** The viewer JS/CSS need to be inlined into the export. Build step has to produce both `dist/` for Chrome AND a string-importable copy of `viewer.js` / `viewer.css` for the SW exporter to embed. Vite plugin or a small post-build script.
